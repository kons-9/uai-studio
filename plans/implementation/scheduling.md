# スケジューリング分析

**優先度:** 高。依存: [スレッドモニタ](thread-monitor.md) と時刻品質が検証された [トレース](tracing.md)。

## 作るもの

- タスクごとに READY 待ち、実行時間、WAITING 理由、preemption、スイッチ回数、優先度を時系列と集計で示す。フレームの「入力が到着したのに inference が起動しない」と「NPU が起動済みで CPU が待っている」を区別する。
- 利用者が対象経路の期待周期／期限を**明示的に設定**した場合にだけ期限超過を報告し、入力時間と結果反映時間を含む end-to-end レイテンシを評価する。期待値を推測してデッドラインミスと断定しない。
- 「優先度を上げる」等の提案はトレース上の READY 待ち、実行中タスク、queue、先行 frame との関連を根拠に候補として表示し、自動変更しない。mutex の所有と待ちの両方が計測できない限り「優先度逆転」とは断定しない。

## 解析規則

`READY→RUN` から dispatch 遅延、`RUN→WAIT` から実行片、queue 送受からデータ待ちを復元。NPU の壁時計時間を CPU 使用率へ加算しない。割込みによる待ち、表示 task と後処理 task の優先度差（現状は [TaskContext](../../userspace/experiment-ai/src/task/task_context.cpp) に定義）を別に扱い、短時間の揺れと継続的な滞留を p50／p95／max と頻度で比較する。

## APP 依存と段階的提供

低容量構成では queue 待ち統計と優先度／状態サンプルから「可能性」を表示し、CPU 使用率と READY 時間は未計測にする。dispatch イベントが取れるときだけスケジュール復元・競合タスク特定を開放する。予測モデルは収集条件が揃ってからホストに追加するので APP の常駐コードを増やさない。

## 完了条件

意図的なカメラ負荷・後処理遅延・推論待ちを別シナリオとして取得し、それぞれ READY 待ち／データ待ち／NPU 待ちの違いを正しく示す。欠落がある窓は数値を出さず、[共通の実機ゲート](README.md#共通の検証ゲート)を通す。
