# 対話型プロファイリング（MCP／関数プローブ）

**優先度:** 低。依存: [トレース形式](tracing.md)、ホストの信頼できる [分析器](dashboard.md)。標準の experiment-ai と共存させるか、別ファームウェアにするかは APP 空き・測りたい対象によって決める。

## 作るもの

- 最初は PC 側でオフライン trace／タスク／NPU／メモリの事実を検索できる読み取り専用の MCP インターフェースを用意する。ボード上の JSON-RPC を前提にしないため、APP のコードと RAM が不要。
- 対話的な実機取得が必要なら、PC の bridge が SWD ダンプ／低頻度の診断要求を扱い、マイコンには固定コマンドだけ実装する。サイズ・認証・timeout・帯域・UART への影響を測定してから載せる。
- 関数単位計測はまず計測対象のコンパイル時ラッパー／固定プローブから始め、対象関数が実際に呼ばれる文脈を維持して時間・呼出回数を記録する。関数を別の RAM にコピーして `call` するだけでは元の関数の呼出箇所・割込み・共有状態の実行時間は計測できない。

## 動的コード転送を使う場合の別設計ゲート

実行時の任意関数バイナリ配置は標準の experiment-ai イメージとは別の**実験用プロファイル**として扱う。配置先・実行権限／MPU・キャッシュ同期・Thumb エントリ・再配置・呼出 ABI・許可 API・時間制限・失敗時復帰・信頼できる転送元を設計／実機検証する。サイズ／エントリポイント確認と MPU のみではカーネル保護や安全な実行を保証できない。プローブは任意既存関数の透過的なフックではなく、指定された安全な実験機能から開始する。

## APP 依存と完了条件

空きゼロならホスト MCP のみ、空きがあり必要性が高いときだけ固定コマンド、独立ファームウェアで実証した後に限定プローブを検討する。別ファームウェア方式は**experiment-ai と同時に動作している情報を取れない**ことを UI に明示する。対象関数の計測誤差と実行文脈を測り、ボード側を変更した構成では [共通の実機ゲート](README.md#共通の検証ゲート)を通す。
